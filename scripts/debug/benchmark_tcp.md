# 本机 TCP 容量与延迟测试

从项目根目录运行：

```powershell
python -m scripts.debug.benchmark_tcp --connections 200 --hold-seconds 3600
```

测试依赖项目运行环境及 `psutil`（本机已安装）。不会读取 `config.json`，模拟服务器只监听 `127.0.0.1`，不会访问真实游戏服务器。模拟服务器在独立进程中运行，结束时自动关闭。

每条连接复用项目的 `GameSocket`、`MessageRouter`、`AppContext` 和每分钟的 `SessionClock` 发送任务。绕过真实 HTTP 登录及玩家初始化，模拟登录应答后开始接收循环。所有连接建立后，才开始共同的一小时维持窗口。每条连接每 5 秒发送一次含 256 字节数据的探测包，通过已有订阅接口等待模拟应答；不创建第二个收包循环，不自动重连。

默认同时建立连接的任务数是 5，与 `AccountManager.connect_all()` 的默认值一致。需要比较同时建连时的排队与延迟，可显式设置 `--connect-concurrency 200`。这个参数控制建立速度，`--connections` 控制最终维持的总数。

当前入口的限制不同：`src/accounts/manager.py:163` 的槽位只限制建连任务，连接建立后继续保留；本地 `batch_send_template.py:91` 的槽位覆盖连接、发送及断开，最多同时维持 5 条；桌面入口 `src/ipc/server.py:352` 对所选账号直接并发执行，没有使用上述 5 个槽位。这里的本机测试不经过桌面 UI。

## 输出

每次运行生成独立的 `evidence/tcp-benchmark/<时间>/` 目录：

- `status.json`：当前进度，每 30 秒更新。只有 `passed` 才表示完整通过。
- `connection-latencies.json`：各连接的 TCP 建立、含策略文件读取的建立耗时、模拟登录应答耗时。
- `samples.jsonl`：活动连接数、最近响应数、探测成功/失败数、客户端及模拟服务器的内存/CPU。
- `summary.json`：最终结论、P50/P95/P99、各连接状态和清理情况。
- `client.log`、`server.log`：本次本机测试的诊断输出。

CPU 百分比以一个逻辑核为 100%；与整机 CPU 百分比不同。RSS 包含 Python、项目模块和测试采样开销。探测延迟样本使用每个样本 8 字节的数组保存，最终报告列出这部分内存。模拟服务器的进程资源单独统计。

TCP 建立耗时不包括等待建连槽位的排队时间；`establish_all_seconds` 是建立全部连接的总耗时。模拟登录不是实际账号登录耗时。往返延迟包含本机编码、发送、模拟应答、解码和消息分发，不等于公网延迟。

通过标准：全部连接建立成功，连续维持指定时长，无断开、无探测超时、无接收解析/会话发送错误，结束时连接全部清理。失败不会用自动重连掩盖；`Ctrl+C` 可结束并保存失败结果。

通过 200 条一小时测试，只证明在本机及该小包负载下至少能维持 200 条连接，不能据此宣称绝对并发上限，也不能推断真实服务器/IP/账号上限或战斗界面的承载能力。
